# experimental-saas-monorepo

A small, real SaaS app built to put [`@anephenix/fastify-resource`](../../)
(the parent repo) and [`@anephenix/fastify-auth`](https://github.com/anephenix/fastify-auth)
to a real test together - not a toy or a unit test, an actual app that
consumes both as npm dependencies, backed by a real SQLite database, with a
real Svelte frontend and a real Cucumber + Playwright end-to-end suite
driving a real browser against real running servers.

## What it is

- **Auth**: password login, magic-link login, TOTP MFA, and forgotten-
  password, all generated by `@anephenix/fastify-auth`'s CLI wizard.
- **API**: a `Project` resource (create/list/delete, scoped per user) built
  with `@anephenix/fastify-resource`'s plugin - the actual library this
  repo publishes.
- **Frontend**: Vite + Svelte 5 - home, signup, login (password and magic-
  link), MFA-login, forgot-password, reset-password, dashboard, and profile
  (with MFA enrollment) pages.
- **Tests**: a self-contained Cucumber + Playwright suite covering
  password/magic-link/TOTP login (including the magic-link+TOTP combo),
  forgotten-password, and logout.

## Why it exists

`fastify-resource` and `fastify-auth` both have their own test suites, but
those tests exercise the libraries in isolation, against fake in-memory
models rather than a real database, and never through a real browser. This
app is the opposite: it's what an actual consumer of both packages would
build, so it catches the class of bug that only shows up when the generated
code meets a real SQL schema and a real UI.

It did exactly that. Building this surfaced three real bugs in
`fastify-auth` that its own test suite had never caught:

- `IUserModelStatic.authenticate()`'s declared return type was missing
  `| null`, even though every strategy relies on it returning `null` on
  failed auth.
- `IRecoveryCodeModel` declared `verify()`/`markAsUsed()` methods that no
  real model implements, breaking `tsc` for any correctly-typed
  `RecoveryCode` model.
- The wizard's generated `RecoveryCode` model tried to `INSERT` its
  transient plaintext `code` field, which has no backing column - this
  fails against any real database, but never showed up against the fake
  models the wizard's own tests use.

All three are fixed upstream in `fastify-auth` as of this example's build.

## How it was generated

This wasn't hand-written from scratch - it follows the same path a real
consumer would:

1. **Scaffolded the monorepo** - a plain npm-workspaces root
   (`packages/api`, `packages/web`, `packages/e2e`), no extra monorepo
   tooling (Turborepo, pnpm, etc.) - the same "just npm scripts" approach
   both `fastify-resource` and `fastify-auth` themselves use.

2. **Generated the auth foundation for real**, by running the actual CLI:

   ```shell
   npx @anephenix/fastify-auth wizard --output src
   # password: yes, magic-link: yes, mfa: totp, forgotten-password: yes
   ```

   This produced `packages/api/src/lib/auth.ts`, `src/models/{User,Session,
   MagicLink,MfaToken,RecoveryCode,ForgotPassword}.ts`, `src/routes/auth.ts`
   and `src/index.ts` - real generated code, then hand-edited in a few
   places (wiring in the database, a dev-only "outbox" instead of
   `console.log` for magic-link codes and reset tokens, service naming).

3. **Wrote Knex migrations** for every table those generated models expect,
   plus one for `projects`.

4. **Registered the `Project` resource** with `fastify-resource`'s plugin,
   scoped per user via `preHandler` (session auth) + `headerParams` (a
   `user_id` resolved from the session, not a real inbound header) +
   `paramsTransform` (to fix a header-is-always-a-string type mismatch) +
   a `customModelAction` (the library's default `update`/`delete` actions
   only scope by `id`, not the extra `headerParams` value - queried by hand
   for those two actions to close that gap; `getAll`/`get`/`create` already
   scope correctly by default). See `packages/api/src/index.ts` and
   `packages/api/src/lib/scopedProjectAction.ts`.

5. **Scaffolded the frontend** with `npm create vite@latest -- --template
   svelte-ts`, then built the 8 pages against the API, with a small hand-
   rolled router rather than a dependency (the route set is small and
   fixed, so ~90 lines of History-API code was less risk than pulling in a
   third-party router of uncertain Svelte 5 compatibility).

6. **Verified the frontend against a real browser** with a throwaway
   Playwright script before the real test suite existed - this is what
   caught the `RecoveryCode` bug above, plus a bug in this app's own
   `api.ts` (sending `Content-Type: application/json` with an empty body on
   bodyless POSTs, which Fastify's parser rejects).

7. **Built the Cucumber suite** last, once the manual flows were proven to
   work - `support/hooks.ts` spins up a real API + web server against a
   throwaway SQLite file and a real headless browser before any scenario
   runs, and tears both down after.

## Reproducing this from scratch

If you wanted to build this yourself against a fresh checkout of both
repos, the recipe is exactly the 7 steps above. The specific commands:

```shell
# 1. Monorepo root
mkdir my-app && cd my-app
# package.json with "workspaces": ["packages/*"]

# 2. Auth foundation
mkdir -p packages/api/src && cd packages/api
npm init -y
npm i fastify @fastify/cookie objection knex better-sqlite3 otplib qrcode \
  @anephenix/auth @anephenix/fastify-resource
npm i -D typescript tsx @types/node @types/better-sqlite3 @types/qrcode
npm i file:../../../fastify-auth   # or the published version, once it is
npx @anephenix/fastify-auth wizard --output src

# 3. Migrations - one per generated model, plus your own resources
npx knex migrate:make create_users_table   # ...repeat per table

# 4. Wire fastify-resource into src/index.ts (see that file for the
#    preHandler/headerParams/paramsTransform/customModelAction pattern)

# 5. Frontend
cd .. && npm create vite@latest web -- --template svelte-ts

# 6. Verify manually (a throwaway Playwright script, or a real browser)

# 7. e2e suite
mkdir -p packages/e2e && cd packages/e2e
npm init -y
npm i -D @cucumber/cucumber playwright tsx better-sqlite3 otplib
npx playwright install chromium
```

The one non-obvious part throughout: **`@anephenix/fastify-auth` isn't
published to npm yet**, so it's installed via a `file:` link to a sibling
checkout rather than a version range - see Requirements below.

## Requirements

**Node 22 LTS** (see `.nvmrc` - `nvm use`). `better-sqlite3`'s prebuilt
binary isn't published for the newest Node major yet, so an `npm install`
under (e.g.) Node 24 falls back to compiling it from source, which can fail
depending on your local C++ toolchain. Node 22 avoids that entirely.

**Both repos checked out as siblings** - this example depends on
`@anephenix/fastify-auth` via a `file:` link (`packages/api/package.json`,
`packages/e2e/package.json`) rather than a registry version, since that
package isn't published yet. Your disk layout needs to be:

```
open-source/
├── fastify-resource/
│   └── examples/experimental-saas-monorepo/   ← this app
└── fastify-auth/                              ← needs `npm run build` run
                                                   at least once, so dist/ exists
```

## Running it

```shell
npm install

# migrate the dev SQLite database
npm run migrate --workspace packages/api

# in separate terminals
npm run dev:api   # http://localhost:3000
npm run dev:web   # http://localhost:5173
```

## Running the e2e tests

```shell
npm run test:e2e
```

This spins up its own API + web servers against a throwaway SQLite file
(`packages/api/data/e2e-test.sqlite3`, regenerated on every run), runs the
full Cucumber suite (password/magic-link/TOTP login, the magic-link+TOTP
combo, forgotten-password, logout) against a real headless Playwright
browser, and tears both servers down afterward - no servers need to be
running beforehand, and nothing here touches the dev database.
